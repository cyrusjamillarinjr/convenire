PURPOSE & STRATEGIC JUSTIFICATION

Why the Agile Model Was Selected for CONVENIRE

Developing an educational hardware assembly puzzle simulator introduces unique technical and pedagogical challenges that traditional linear software models (like Waterfall) fail to address. Agile's iterative and flexible nature proved essential for the following four fundamental reasons:

01

Iterative Mechanics & Hitbox Calibration

Empirical Drop-Zone Tuning vs. Theoretical Specs

Physical hardware assembly requires pixel-perfect spatial precision. Socket coordinates (e.g. LGA-1700 CPU, DDR5 dual-channel slots, PCIe x16 latches) cannot be finalized purely on paper. Agile allowed our team to code quick prototypes, test drop-zone tolerances using our dedicated debug_dropzones.html calibration tool, and iteratively fine-tune coordinates across multiple screen resolutions.

Tactile Game Feel
02

Student & Instructor Feedback Integration

Continuous Co-Design with Real Learners

CONVENIRE is an educational tool for BSCS students at North Negros College. Rather than waiting for a post-launch evaluation, Agile enabled our team to conduct sprint reviews at the end of each stage. Feedback from computer architecture professors and peer students led to immediate improvements, such as adding visual orientation notches, dual-channel RAM pairing rules, and Cat6 crimping standards.

Pedagogical Accuracy
03

Early Working Vertical Slices & Risk Reduction

Playable Prototypes Delivered from Sprint 2

In linear models, integration occurs late in the project timeline, creating high risk for game-breaking bugs. By utilizing Agile, our team delivered a fully playable vertical slice of Stage 1 (Motherboard Assembly) in Sprint 2. This proved the viability of our 2D HTML5 canvas, drag-and-drop mechanics, and Web Audio synthesis early, eliminating technical debt and architectural risks.

De-risked Architecture
04

Cross-Functional Team Velocity & Synergy

Parallel Development for 5 Student Specialists

Our 5-member team divided roles across Lead Architecture, UI/UX Visual Assets, Backend Systems, Interactive UI Components, and Database Engineering. Daily standup check-ins and sprint backlog grooming allowed artists to supply 3D hardware graphics while frontend engineers coded drop zones concurrently, maintaining high velocity without blocking one another.

High Team Velocity
LIFECYCLE EXECUTION

The 6-Phase Agile Sprint Loop in CONVENIRE

Each 2-week sprint cycle repeated this structured 6-phase engineering loop, transforming curriculum learning competencies into fully tested, playable game mechanics:

PHASE 01 INPUT
Sprint Planning & Backlog Grooming

The team decomposes educational goals into actionable user stories with explicit acceptance criteria. Example: "As a player, I must correctly orient the CPU triangle notch before socket clamping." Tasks are estimated and committed to the sprint backlog.

Deliverable: Sprint Backlog & Story Points
PHASE 02 DESIGN
Component UI/UX & Hardware Modeling

UI designers craft cyberpunk HUD interfaces, neon glow states, and prepare high-resolution component sprites (CPU, GPU, RAM, cables). Layout coordinates are measured against real ATX motherboard standards for high authenticity.

Deliverable: UI Wireframes & 2D/3D Assets
PHASE 03 BUILD
Iterative Coding & Feature Engineering

Engineers implement modular game logic: pointer drag-and-drop handlers, bounding-box hit tests, audio synthesis triggers (Web Audio API), score multipliers, and dynamic diagnostic feedback systems.

Deliverable: Playable Feature Modules
PHASE 04 VERIFY
Empirical Calibration & Playtesting

Rigorous quality assurance using calibration tools (such as debug_dropzones.html) to verify hitbox boundaries, snapping magnetic radii, browser responsiveness, and mobile touch support without regressions.

Deliverable: Calibrated Drop-Zone Matrix
PHASE 05 EVALUATE
Sprint Review & Retrospectives

Live demonstration of sprint increments to North Negros College CS faculty and peer learners. The team reviews what went well, identifies friction points, and adjusts gameplay difficulty or clarity for the next sprint.

Deliverable: Stakeholder Feedback & Action Items
PHASE 06 RELEASE
Incremental Deployment & Staging

The verified playable stage is integrated into the web release branch. Students can immediately access the new challenges online, verify their scores, and submit bug reports or usability suggestions.

Deliverable: Live Incremental Web Build
METHODOLOGY EVALUATION

Why Agile Triumphed Over the Waterfall Model

A side-by-side comparative analysis demonstrating why traditional linear methodologies were unsuitable for our interactive educational puzzle game:

EVALUATION FACTOR AGILE MODEL (CHOSEN) WATERFALL MODEL (REJECTED)
Requirement Flexibility Highly Adaptive — Incorporates instructor feedback and new hardware specs between sprints. Rigid — Changes require formal rework of requirements, causing major schedule delays.
Playable Increments Sprint 2 Working Slice — Playable Motherboard stage available within weeks for real testing. Delayed to End — Working game is only visible at the final phase; impossible to test early feel.
Hitbox & Calibration Testing Continuous Every Sprint — Empirical calibration of drop zones and physics in real time. Postponed to QA — Misaligned hitboxes or confusing mechanics discovered too late to easily refactor.
User & Student Feedback Continuous Sprint Demos — BSCS students and professors test each stage progressively. Post-Delivery Only — Feedback received only after deployment, risking poor educational adoption.
Team Risk Management Iteratively De-risked — Unknowns in canvas rendering and audio synthesis resolved early. High Risk — Unverified technical assumptions compound into catastrophic integration bottlenecks.
Team Structure Collaborative Synergy — 5 student developers coordinate in parallel via daily standups. Sequential Silos — Frontend waits for backend, designers idle while engineers code.

JavaScript · Web Audio Synth & Snap Physics game/javascript/stage1.js (Extract) 
// PROCEDURAL AUDIO SYNTHESIZER (ZERO AUDIO LAG)
const soundFx = {
  snap: function() {
    const ctx = getAudioContext();
    const osc = ctx.createOscillator();
    const gain = ctx.createGain();
    osc.type = 'triangle';
    osc.frequency.setValueAtTime(180, ctx.currentTime);
    osc.frequency.exponentialRampToValueAtTime(60, ctx.currentTime + 0.12);
    gain.gain.setValueAtTime(0.3, ctx.currentTime);
    gain.gain.exponentialRampToValueAtTime(0.001, ctx.currentTime + 0.12);
    osc.connect(gain);
    gain.connect(ctx.destination);
    osc.start();
    osc.stop(ctx.currentTime + 0.12);
  }
};

// CALIBRATED EUCLIDEAN SNAP TOLERANCE ENGINE
function checkDropZone(componentX, componentY, targetZone) {
  const rect = targetZone.getBoundingClientRect();
  const zoneCenterX = rect.left + rect.width / 2;
  const zoneCenterY = rect.top + rect.height / 2;

  // Calculate distance via Pythagorean Theorem
  const distance = Math.hypot(componentX - zoneCenterX, componentY - zoneCenterY);
  const TOLERANCE_PX = parseFloat(targetZone.dataset.tolerance) || 40;

  if (distance <= TOLERANCE_PX) {
    soundFx.snap();
    lockComponentInSocket(targetZone);
    return true;
  }
  return false;
}

PHP 8.x · Student Session Auth & Score Logging API game/php/save_progress.php (Extract) 
<?php
header('Content-Type: application/json');
require_once 'db_connect.php';

// 1. Parse JSON Payload from Client Fetch Request
$data = json_decode(file_get_contents("php://input"), true);
$studentIdNumber = trim($data['studentId'] ?? '');
$stage           = intval($data['stage'] ?? 0);
$score           = intval($data['score'] ?? 0);

// 2. Validate Parameters Against Injection
if (!$studentIdNumber || $stage < 1 || $stage > 3) {
    http_response_code(400);
    echo json_encode(["success" => false, "message" => "Invalid parameters."]);
    exit;
}

// 3. Secure Prepared SQL Statement Execution
$now = new DateTime();
$playDate = $now->format('Y-m-d');
$playTime = $now->format('H:i:s');

$insert = $conn->prepare(
    "INSERT INTO game_logs (student_id, stage, play_date, play_time, score) VALUES (?, ?, ?, ?, ?)"
);
$insert->bind_param("sissi", $studentIdNumber, $stage, $playDate, $playTime, $score);
$insert->execute();

// 4. Return Normalized JSON Telemetry to Frontend
echo json_encode([
    "success" => true,
    "message" => "Stage progress logged.",
    "log_id"  => $insert->insert_id
]);
$conn->close();
?>
